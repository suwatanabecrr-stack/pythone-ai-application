# Streamlit + LLM API アプリのセキュリティチェック

Streamlit で作った LLM アプリを調べ、問題点と直し方を**セキュリティレポート**にまとめる。
こうしたアプリで実際によく起こる被害は、高度な攻撃より次のようなものである。

1. **APIキーが漏れて他人に使われ、請求が来る**（直書き、git の履歴、画面への表示）
2. **公開したアプリを知らない人に使い放題にされ、請求が来る**
3. **利用者どうしでデータが混ざる**（Streamlit のキャッシュやグローバル変数は全員で共有される）
4. **LLM の出力をそのまま HTML・コード・コマンドとして扱ってしまう**

この順で重みを置いて調べる。理屈の上だけの問題を並べるより、このアプリで本当に起こりうる被害をはっきり伝えるほうが役に立つ。

## 進め方

### 1. 前提をつかむ

- プロジェクトの README / CLAUDE.md を読み、アプリの目的と「あえてそうしている設計」を確認する（例：「認証は付けない」という方針）。方針に反する修正をそのまま勧めず、方針を守ったうえでの対策を書く（例：コードに認証を足すのではなく、公開先の閲覧制限を使う）。
- **公開状況**（ローカル専用か、ネットに公開するか、すでに公開中か）は深刻度を大きく左右する。README・デプロイ用ファイル・依頼の文面から推測できなければ、ユーザーに一度だけ聞く。答えが得られなければ「公開する場合」を前提に評価し、その前提をレポートに書く。

### 2. 一次スキャンを実行する

同梱のスクリプトで、秘密情報と注意が必要な書き方の候補を洗い出す（標準ライブラリだけで動く。見つかったキーは伏せ字で表示される）。

```bash
python -I <このスキルのフォルダ>/scripts/scan.py <プロジェクトのフォルダ>
```

Windows で文字化けやエンコードのエラーが出るときは、環境変数 `PYTHONIOENCODING=utf-8` を付けて実行する。プロジェクトに `.venv` があれば、その Python を使ってよい。

**スキャンで見つかったものは「調べる候補」にすぎない。** 該当箇所のコードを必ず読み、本当に問題か、どんな条件で被害が出るかを判断する。誤検知（問題でないもの）をレポートに混ぜると信頼を失う。逆に、スキャンは決まった書き方を文字で探すだけなので、データの流れ（ユーザー入力 → プロンプト → LLM 出力 → 表示・実行）は自分でコードを読んで追う。

### 3. 項目ごとに調べる

`references/checklist.md` を読み、A〜G の項目を順に確認する。

- A. 秘密情報 / B. Streamlit 特有 / C. LLM 特有 / D. 利用料金・乱用 / E. 一般的なコード / F. 依存ライブラリ / G. 公開・運用

依存ライブラリの既知の脆弱性を調べる `pip-audit` が入っていない場合は、**入れてよいかユーザーに確認してから**インストールする（環境を変えるため）。確認できなければ実行せず、「調べられなかったこと」に書く。

### 4. 深刻度を決める

| 深刻度 | 意味 |
|---|---|
| 🔴 重大 | すぐに被害が出うる。キーの漏えい、任意コードの実行など。今すぐ対応する |
| 🟠 高 | 条件がそろえば大きな被害が出る。公開前に必ず直す |
| 🟡 中 | 被害は限定的か、起こすのに手間がかかる。早めに直す |
| 🔵 低 | 念のための強化 |
| ⚪ 情報 | 問題ではないが知っておくとよいこと |

checklist.md の目安は「公開あり」の前提で書いてある。ローカル専用で使う場合、外部の人が関わって初めて起こる問題（乱用、利用者間のデータ混在、XSS など）は1〜2段階下げ、「公開するときは🟠高になる」と書き添える。キーの直書きや git 履歴への混入は、ローカル専用でも下げない。ファイルの共有、バックアップ、うっかりした公開で漏れるからである。

### 5. レポートを書く

プロジェクトのルートに `security-report_YYYY-MM-DD.md` として保存する（同名ファイルがある場合は `_2` を付ける）。下のテンプレートに従う。

レポートを書くときのルール：

- **秘密情報の値は絶対に書かない。** 書くのは「`app.py:12` に Google APIキー（`AIza…`、39文字）」のような場所と種類だけにする。レポート自体が漏えい元になるのを防ぐため。
- 読む人はプログラミング初心者かもしれない。専門用語には一言の説明を添え（例：「XSS（他人のブラウザで勝手にプログラムを動かされる攻撃）」）、「何が起こりうるか」は具体的な場面で書く。
- 指摘には必ず `ファイル:行` を付け、直し方は実際のコードに合わせた修正前・修正後を示す。
- 問題がなかった項目も短く載せる。何を確認したのかが分かれば、レポートの範囲を信頼できる。
- プロジェクトの CLAUDE.md などで言語の指定があれば従う。なければユーザーとの会話の言語で書く。

### 6. 報告して、修正するか確認する

チャットでは、総合評価・深刻度ごとの件数・対応を急ぐ上位の指摘だけを短く伝え、レポートのファイルパスを示す。そのうえで「どの指摘を直しますか？」と確認する。**ユーザーの確認なしにコードを変えない。** セキュリティの修正は動作を変えることがあり、方針と関わる判断も含むためである。修正したら、プロジェクトに書かれた確認手順（テストや起動チェック）を実行する。

キーが漏れている（または漏れた可能性がある）場合は、コードを直すだけでは不十分である。**プロバイダの管理画面でキーを無効化して作り直す**よう、最初に、はっきり伝える。

## レポートのテンプレート

```markdown
# セキュリティレポート：<アプリ名>

- 実施日：YYYY-MM-DD
- 対象：<フォルダパス>（主なファイル：app.py ほか）
- 構成：Streamlit <版> / <LLM SDK> / <その他>
- 前提とした公開状況：<ローカル専用 / 公開予定 / 公開中>（<根拠：ユーザーの回答・README など>）

## 総合評価

<1〜3文。「公開前に直すべき問題が2件あります」のように、結論を先に書く>

| 深刻度 | 件数 |
|---|---|
| 🔴 重大 | 0 |
| 🟠 高 | 0 |
| 🟡 中 | 0 |
| 🔵 低 | 0 |
| ⚪ 情報 | 0 |

## 指摘事項

### [1] 🟠 高：<短い題名>

- **場所**：`app.py:54`
- **分類**：<A5 秘密情報の画面表示 など。checklist.md の ID>
- **何が問題か**：<コードが何をしているか>
- **起こりうること**：<具体的な被害の場面。前提条件があれば書く（例：公開した場合のみ）>
- **直し方**：
  <手順と、修正前・修正後のコード>

（深刻度の高い順に並べる）

## 問題がなかった項目

- ✅ APIキーの直書きなし（コード・設定・ドキュメント）
- ✅ `.env` は `.gitignore` で除外済み
- …

## 調べられなかったこと・利用者が確認すること

- <例：pip-audit を実行していない / LLM プロバイダの予算アラートの設定 / 公開先の閲覧制限>

## 次にやること（おすすめの順）

1. …
2. …
```
